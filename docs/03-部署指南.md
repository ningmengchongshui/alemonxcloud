# xCloud 部署指南

本文默认以单台 `xcloud-tunnel-gateway` 部署自建节点数据平面：控制面以 Docker Compose 运行；平台节点运行 `xcloud-agent` systemd 服务；自建节点运行 `xcloud-control` systemd 服务。MySQL、Redis、RabbitMQ 是外部独立服务，不由本项目的 Compose 创建。

## 1. 生产前置条件

- Linux、Docker Engine、Docker Compose Plugin、Nginx、systemd。
- 可访问的 MySQL、Redis、RabbitMQ，并已为 xCloud 创建数据库与账号。
- DNS：`xcloud.alemonjs.com`、`tunnel.alemonjs.com`、`*.alemonjs.com`。
- TLS：主站、隧道域名和泛域名证书。自建节点入口使用 `control-r<哈希>.alemonjs.com`，平台实例使用 `xcloud-r<哈希>.alemonjs.com`。
- 一台 Gateway 主机，以及共享的 MySQL/Redis。双 Gateway 集群和 Gateway 间 mTLS 是后续高可用选项。

不要将 Agent Token、Gateway 命令 Token、数据库密码或 OIDC 密钥提交到仓库。

## 2. 部署控制面

在控制面主机检出项目，创建配置文件：

```bash
cp .env.example .env
openssl rand -base64 32 # 用于 XCLOUD_NODE_TOKEN_ENCRYPTION_KEY
openssl rand -hex 32    # 用于 XCLOUD_TUNNEL_COMMAND_TOKEN
```

必须填写 `.env` 中的 MySQL、Redis、RabbitMQ、OIDC、指标令牌、实例域名与数据根目录。生产模式缺项会拒绝启动。至少需要下列 Tunnel 配置：

```dotenv
XCLOUD_TUNNEL_URL=https://tunnel.alemonjs.com
XCLOUD_TUNNEL_INTERNAL_URL=https://tunnel-internal.alemonjs.com
XCLOUD_TUNNEL_COMMAND_TOKEN=与所有 Gateway 的 GATEWAY_COMMAND_TOKEN 相同
```

`XCLOUD_TUNNEL_INTERNAL_URL` 只供控制面调用 `/command`、`/terminal` 与 `/proxy`；可通过内网或受 TLS 保护的 Gateway 域名提供。Gateway 使用 `XCLOUD_TUNNEL_COMMAND_TOKEN` 鉴权，不依赖来源 IP 白名单。它不是用户接入 Token。完整变量边界见 [配置参考](00-配置参考.md)。

启动并检查：

```bash
docker compose up -d --build
docker compose ps
curl -fsS http://127.0.0.1:13082/healthz
curl -fsS http://127.0.0.1:13082/readyz
```

首次启动会执行内置 SQL 迁移，并记录在 `xcloud_schema_migrations`。应先备份数据库，在灰度环境启动一次并核对迁移记录；已发布的迁移文件不可修改，只能新增下一个版本。

## 3. 部署单台 Tunnel Gateway

在 Gateway 主机安装构建产物：

```bash
cd gateway
go build -o xcloud-tunnel-gateway .
sudo install -d -m 0750 /opt/xcloud-tunnel-gateway /etc/xcloud-tunnel
sudo install -m 0755 xcloud-tunnel-gateway /opt/xcloud-tunnel-gateway/
sudo install -m 0644 ../deploy/xcloud-tunnel-gateway.service /etc/systemd/system/
# sudo install -m 0600 ../deploy/xcloud-tunnel-gateway.env.example /etc/xcloud-tunnel/gateway.env
# sudoedit /etc/xcloud-tunnel/gateway.env
sudo systemctl daemon-reload
sudo systemctl enable --now xcloud-tunnel-gateway
```

默认配置 `GATEWAY_MODE=single`，只需要 `GATEWAY_ID`、MySQL、Redis 与 `GATEWAY_COMMAND_TOKEN`；不需要 `GATEWAY_INTERNAL_URL`、`18443`、CA 或 mTLS 证书。

验证 Gateway：

```bash
systemctl status xcloud-tunnel-gateway
curl -fsS http://127.0.0.1:13072/healthz
```

公网 Nginx 将 `/connect` 转给该 Gateway。控制面重启不会中断已建立的 Gateway 设备连接。

需要高可用时，再在第二台主机部署相同服务，并将两台设为 `GATEWAY_MODE=cluster`；此时才配置 `GATEWAY_INTERNAL_URL`、`GATEWAY_INTERNAL_LISTEN=:18443` 与 Gateway 间 mTLS 证书。详见 [配置参考](00-配置参考.md)。

## 4. 配置 Nginx

以 [`deploy/nginx.conf`](../deploy/nginx.conf) 为当前合并示例。部署时：

1. 把证书的 `ssl_certificate` 与 `ssl_certificate_key` 指令放在各 `server` 块或上层 `http` 配置中；示例为避免绑定具体证书路径而省略了这两行。
2. 让 `tunnel.alemonjs.com/connect` 代理到 Gateway 公网监听地址 `13072`，并保留 WebSocket Upgrade 头。
3. 让 `tunnel-internal.alemonjs.com` 代理 Gateway 的 `/command`、`/terminal`、`/proxy`；Gateway 以命令 Token 鉴权，不按控制面来源 IP 拦截。
4. 让主站代理到控制面 `13082`；所有 `xcloud-r<哈希>` 实例域名均代理到控制面 `/__instance_proxy`，由控制面选择平台节点或自建节点。
5. 执行 `nginx -t` 后再 reload，并将 80 统一重定向至 443。

旧 `/__control_proxy` 已返回 `410 Gone`，不能再作为自建服务入口使用。

## 5. 安装平台裸机 Agent

平台节点上的 Agent 是 systemd 服务，不是 Docker 容器：

```bash
docker network create xcloud_network
make agent-build
sudo install -d -m 777 /var/lib/xcloud/instances
sudo install -m 777 agent/xcloud-agent /usr/local/bin/xcloud-agent
sudo install -m 777 deploy/xcloud-agent.service /etc/systemd/system/
# sudoedit /etc/xcloud-agent.env
sudo systemctl daemon-reload
sudo systemctl enable --now xcloud-agent
```

`/etc/xcloud-agent.env` 至少包含：

```dotenv
AGENT_ADDR=0.0.0.0:13092
XCLOUD_AGENT_TOKEN=节点独立的长随机令牌
XCLOUD_DOCKER_NETWORK=xcloud_network
XCLOUD_INSTANCE_DATA_ROOT=/var/lib/xcloud/instances
```

防火墙只允许控制面 Docker 网段 `172.30.0.0/24` 与本机访问 `13092`；禁止直接暴露公网。随后在超级管理台新增节点，填写 Agent URL 与该节点令牌，等待心跳变为健康后再启用调度。完整能力说明见 [Agent 节点](04-Agent节点.md)。

## 6. 用户自建节点接入

用户在“自建节点”页面生成一次性接入 Token。在用户服务器安装 Docker 和 Docker Compose 后：

```bash
cd control
go build -o xcloud-control .
sudo install -d -m 0700 /etc/xcloud-control /var/lib/xcloud-control/instances
sudoedit /etc/xcloud-control/config.json
sudo chmod 777 /etc/xcloud-control/config.json
# sudo ./xcloud-control install
# sudo ./xcloud-control run
sudo systemctl daemon-reload
sudo systemctl enable --now xcloud-control
```

无需手工创建 Docker 网络。`xcloud-control` 会在首次心跳或创建实例时检查 Docker、Docker Compose、数据目录，并自动创建默认的 `xcloud_network`。如需覆盖数据盘或网络名，可选创建 `/etc/xcloud-control.env`：

```dotenv
XCLOUD_CONTROL_DATA_ROOT=/var/lib/xcloud-control/instances
XCLOUD_DOCKER_NETWORK=xcloud_network
```

配置文件最小内容如下，`enrollToken` 必须是用户刚生成的 Token：

```json
{
  "tunnelURL": "https://tunnel.alemonjs.com",
  "enrollToken": "一次性接入Token"
}
```

首次连接时客户端生成 Ed25519 设备私钥，并把已注册的设备 ID 与凭证原子写回此文件。配置文件必须保持 `0600`，用户服务器无需开放任何入站端口。验证：

```bash
systemctl status xcloud-control
journalctl -u xcloud-control -f
```

旧版本地目标 URL 设备必须重新生成 Token 接入；新版本只接受平台审核镜像，并只操作带 `xcloud.managed=true` 标签的实例。

## 7. 发布验收与回滚

发布前至少演练：OIDC 登录、节点心跳、钱包购买、资源不足拒绝、平台与自建节点的创建/访问/日志/文件/终端、Gateway 任一台重启、设备断线重连、退款后服务不中断，以及实例两阶段销毁。

若控制面发布失败，停止新容器并回滚至上一镜像；**不要**回滚已经执行的数据库迁移。迁移修复必须以新的递增迁移完成。Gateway 或 Agent 回滚前应确认其 API/协议能力仍与控制面兼容；旧版自建反代不会被重新启用。
