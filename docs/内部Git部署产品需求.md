# xCloud 内部 Git 部署模式产品需求

版本：0.3 评审稿  
日期：2026-10-04  
状态：产品设计，尚未实现。本文区分用户已确定边界与建议首期方案；不代表现有系统已经具备这些能力。

## 1. 产品定位与目标

为内部白名单用户提供 Git 驱动的持续 Docker 运行平台。Git 管理代码来源与版本，执行任务准备镜像并应用配置，Docker 服务在任务结束后长期运行；平台持续管理容器、网络、端口、存储及实际状态。用户在独立页面指定仓库，通过预检确认配置，再创建和管理包含一个或多个服务的项目。

解决三个问题：部署仓库已有的 Compose 项目；执行项目所需的镜像构建；明确知道部署了哪个版本、失败在哪一步、当前服务是否仍在运行。

用户侧统一使用“Git 项目”名称，避免把多服务项目强行呈现为现有单镜像实例。首期人工触发部署，面向了解仓库内容的内部用户。

### 1.1 用户已确定的边界

- 仅限内部白名单用户；普通用户不显示入口、提示或宣传。
- 使用全新路由页、管理接口和业务模式，与现有固定镜像实例隔离。
- 创建时指定 Git 仓库地址，并持续管理仓库连接、同步和部署版本。
- 仓库的应用类型、语言和具体代码内容不预先确定，平台按 Git 与 Docker 契约处理。
- 需要独立端口管理；执行任务结束后，服务与资源继续受平台管理。
- 一个项目可以包含多个 Compose 单元，每个单元又可以包含多个服务。
- 仓库根目录的 `docker-compose.yml` 和 `.env` 是默认配置约束。
- `xcloud.config.yaml` 可选，只负责 Compose 执行命令和后续额外操作。
- 支持如下命令设置，不擅自补充构建参数：

```yaml
build:
  command: up -d
```

- Git 模式授权与 `host.docker.internal` 授权分别管理，不能相互代替。

### 1.2 建议首期方案

以下内容是本需求建议，尚未由用户逐项确认：专用执行节点；仅支持管理员允许的 HTTPS Git 来源；支持公共仓库及凭证引用的私有仓库；默认命令为 `up -d --build`；持久数据优先使用命名卷；额外脚本操作安排在下一期。

首期不包含公开注册使用、镜像商城、套餐购买、钱包扣费、自动续费、自动 Webhook、分支预览环境、滚动发布、平台数据库备份，以及自动数据回滚。

以下是具体项目在特定版本中的用户反馈和官方说明，用于提炼设计要求，不代表所有平台都有相同问题，也不将已关闭问题描述为当前未修复缺陷。查阅日期为 2026-10-04。

| 公开证据 | 反映的问题 | 本产品采用的要求 |
| --- | --- | --- |
| Coolify 讨论 #7498，2025-12：用户反馈自定义 pull 命令被追加 build 参数导致失败 | 平台隐式加工命令会改变用户意图 | 精确保留支持范围内的命令参数；不自动追加 build-arg，不把所有部署等同于构建 |

| Coolify 问题 #1996，2024-04：仓库中 Compose 引用的配套文件未被完整复制 | 只取 Compose 文件不足以运行真实项目 | 保留完整代码版本，支持仓库内相对路径配置文件和构建上下文 |

| Coolify 讨论 #3177，2024-05：请求识别 Compose 数据库并提供备份视图 | 多服务部署会包含状态数据 | 数据责任明确；代码版本恢复不等于数据库恢复，首期不提供误导性的自动回滚按钮 |

## 3. 权限与入口

### 3.1 权限模型

新增独立的 Git 部署白名单，以用户 ID 为授权依据，保存授权状态、操作管理员、时间、备注和变更历史。

| 角色 | 可执行操作 |
| --- | --- |
| 普通用户 | 无入口；不能创建、读取或操作 Git 项目 |
| Git 白名单用户 | 创建自己的项目，查看服务与日志，部署、启动、停止、重启、删除自己的项目 |
| 管理员 | 管理白名单、执行节点、项目限额，查看全局任务和审计；实施紧急停止 |
| 已撤销白名单的项目所有者 | 不得创建、新部署、修改环境或执行代码；可查看、停止和申请/执行受控删除已有项目 |

建议撤销白名单保留查看、停止、删除权限，便于用户收尾；暂停启动和重启权限，避免重新执行仓库代码。不自动销毁正在运行的项目。管理员可单独停止项目。

每个写操作同时检查用户授权、项目所有权、执行节点策略。排队任务在开始执行时再次检查授权；管理员撤销授权后，尚未执行的部署应结束为“权限已撤销”。运行中的任务由管理员选择取消，撤销授权本身不能被误报为已停止容器。

Git 白名单不自动授予宿主机访问、特权容器或任意脚本权限。

### 3.2 独立页面

建议用户路由：`/git`、`/git/new`、`/git/:projectId`。项目详情包含仓库、服务、部署、环境、端口和存储视图。建议管理路由：`/super/git`，包含白名单、项目、部署任务、执行节点、端口与资源视图。

管理员可直接按用户 ID/账号检索加白，填写备注并撤销，不依赖用户先创建项目。普通用户直接进入 Git 路由时返回统一无权限页面，不展示申请开通推广。

页面状态覆盖加载、空列表、仓库不可达、无可用节点、预检失败、部署失败、节点失联与权限撤销。窄屏和明暗主题均应可用；权限与状态不只依靠颜色表达。

## 4. 创建项目流程

1. 填写项目名称、仓库地址、分支/标签/提交；未填版本时解析仓库默认分支，不假定所有仓库都叫 main。
2. 私有仓库选择凭证引用；执行目标从管理员允许的节点中选择。没有可用节点时不允许提交任务。
3. 点击“检查仓库”。系统获取一个确定提交，读取根目录配置，执行静态策略检查和 Compose 配置解析，不执行 Dockerfile、仓库脚本或业务容器。
4. 展示提交 SHA、实际部署命令、服务列表、镜像或构建来源、端口、挂载、所需环境变量和阻断项。用户补充项目环境值，并对最终配置重新预检。
5. 点击“创建并部署”。绑定预检通过的提交、配置版本、策略版本和执行目标，创建异步部署记录。
6. 进入项目详情，显示真实阶段日志及运行状态。失败时保留项目和失败记录，允许修正后重新检查部署。

预检结果有有效期；环境值、仓库版本或执行策略变化后失效。提交时发现分支已前进，不静默换成新提交：仍部署已检查提交，或由用户重新检查新版。

创建请求须幂等；重复点击或网络重试不能创建多个同名副本并发执行。克隆失败要区分地址错误、认证失败、版本不存在与超时，禁止无限等待交互式凭证输入。

## 5. 仓库配置契约

### 5.1 文件与路径

| 文件 | 首期约定 |
| --- | --- |
| docker-compose.yml | 默认入口为根目录文件；支持登记多个 Compose 单元及仓库内相对文件路径，各单元分别检查 |
| .env | 根目录是默认来源；多单元可指定自己的环境文件，优先级与隔离规则见第 17 节；缺必需变量时阻断 |
| xcloud.config.yaml | 根目录可选；存在时必须合法，错误时不退回默认命令 |
| Dockerfile、配置文件等 | 按仓库相对路径使用；不得仅下载三个约定文件 |
| 子模块、Git LFS | 首期暂不支持；检测到实际依赖时明确阻断，不悄悄获取不完整代码 |
| 多 Compose 与子目录入口 | 首期支持多个独立单元；首期每个单元使用一份 Compose 文件，多文件合并 override 另行设计 |

仓库版本目录保留到相关容器不再引用它为止。仓库内只读配置文件可作为 bind mount 使用；可写持久数据首期要求命名卷。仓库 bind mount 首期按只读处理，不能把写入仓库目录的数据当作跨版本持久数据；确需可写 bind mount 时，进入后续由管理员授权的持久目录能力。

所有路径经规范化后检查越界和符号链接，不能通过 `../` 或软链接访问其他项目及宿主机敏感目录。不得默默创建缺失的文件为目录。

### 5.2 环境变量

项目有效环境值优先级建议为：项目显式覆盖值 > 仓库 .env。平台运行进程的环境不能意外参与项目变量插值；平台控制变量使用保留名称并拒绝覆盖。

必须区分 Compose 插值、服务 `env_file/environment`、构建 `build.args/secrets`。读取 .env 不代表把所有值自动注入每个容器或 Dockerfile。仓库明确引用的 env_file 按路径解析；根目录 .env 被引用时，应与本次有效环境快照保持一致。预检展示变量名称、来源和缺失项，不回显敏感值。

环境更新先保存新版本，随后用户手动部署才生效。旧部署保留受控的环境版本引用；日志、接口和前端持久化不保存凭证明文。真实敏感信息建议通过项目配置提供，仓库 .env 主要承担默认值，但产品不会擅自改用 .env.example。

Git 读取凭证仅供拉取仓库，不能自动传给构建或运行容器。构建确需额外秘密时必须显式授权；不把所有环境变量转换成 build args。Docker 官方建议通过构建 secrets 处理秘密，而非 ARG/ENV；这不意味着授权给不可信构建的秘密不会被其读取。[Docker 构建秘密文档](https://docs.docker.com/build/building/secrets/)

### 5.3 xcloud.config.yaml 的首期语义

支持范围明确限定为 `build.command`：

```yaml
build:
  command: up -d
```

不提供配置或未指定 command 时，建议默认：

```yaml
build:
  command: up -d --build
```

`build` 名称沿用用户约定，字段控制的是部署时的 Compose 命令；不意味着每次都强制 build。

- 平台固定执行 docker compose，将 command 解析成参数列表，不交给宿主机 shell。
- 首期支持 `up`、`-d/--detach`、`--build`、`--no-build`、`--pull always|missing|never`、`--force-recreate`。必须后台启动，冲突参数与未知参数阻断；不支持服务名子集和 profiles。
- 项目名、Compose 文件、环境文件、工作目录由平台控制，用户不得用 -p、-f 等覆盖。
- 拒绝 shell 运算符、命令替换、重定向以及 `down -v`、`exec`、`run` 等非首期操作。
- 对 `up -d` 不追加 --build；但 Compose 原生行为仍可能为缺失镜像或仓库 pull_policy 执行构建/拉取。需要严格禁止构建时使用 --no-build。
- 不默认强拉 latest；拉取行为由仓库策略或显式 --pull 参数决定。详情展示本次实际镜像 ID/digest，不能只记录 tag。
- 额外操作与脚本扩展安排 P1；schema 尚未确定。首期未知字段明确报错，不能静默执行或忽略。

Docker 官方区分 --build、--no-build、--pull 和后台运行选项。因此“没有追加 --build”与“保证完全不发生构建”必须分别表达。[Docker Compose up 文档](https://docs.docker.com/reference/cli/docker/compose/up/)

## 6. 项目、服务与部署记录

一个 Git 项目包含多个 Compose 单元，每个单元包含多个服务。Compose namespace 按项目与单元生成，保留各单元的仓库服务名称及内部服务 DNS，避免改名导致 web 找不到 db。同项目不同单元默认也独立，跨单元通信由显式授权的网络关系建立。

| 对象 | 核心信息 |
| --- | --- |
| Git 项目 | 所有者、仓库、目标 ref、执行节点、单元集合、项目配置版本、最近尝试部署、启停意图 |
| Compose 单元 | 单元 ID、名称、文件与工作目录、环境版本、namespace、部署次序、启用状态、当前运行部署 |
| 单元部署 | 项目部署 ID、单元、目标提交、命令、配置快照、阶段与结果；允许单元实际运行版本不一致 |
| 部署记录 | 提交 SHA、配置摘要、实际参数、环境版本引用、策略版本、执行阶段、日志、起止时间、结果及镜像信息 |
| 服务 | 所属单元、原始服务名称、容器、运行状态、健康状态、重启次数、端口和资源 |
| 持久资源 | 项目归属、命名卷、使用状态、保留/清理结果 |
| 白名单授权 | 用户、授权状态、操作管理员、时间、备注及历史 |

“最近部署失败”不能覆盖“旧版本仍运行”的事实。服务运行状态与部署任务状态分别展示；正在执行部署也不能把所有旧容器显示为已停止。

详情页建议包含：概览、服务、部署记录、环境配置、存储。服务日志必须可选择服务；构建日志与运行日志分开。首期不提供宿主机终端；容器终端放入后续单独授权能力。

访问入口与端口在项目页面独立管理，后台项目可不发布端口。首期管理多个服务的 TCP/UDP 映射，并可为 HTTP 服务配置访问入口；公网开放须符合节点与管理员授权策略。端口分配与 Compose 的一致性见第 15 节。不得继承固定的 alemonx 服务名、17390 端口、健康检查或旧模式默认挂载。健康规则来自 Compose；缺少 healthcheck 时只显示“运行中，未配置健康检查”。

## 7. 部署与生命周期

### 7.1 部署流程

排队 → 获取指定提交 → 配置及策略检查 → 准备镜像（按命令和 Compose 策略）→ 应用 Compose → 核验服务 → 结束。

日志给出当前阶段、开始时间和错误原因，不显示虚构百分比。任务有阶段超时与总超时、每节点并发上限、项目互斥锁；首期建议每节点一个部署并行，具体资源与超时由管理员配置。不能出现失败任务永久占锁、阻塞全部项目。

部署成功定义：命令成功退出，预期常驻服务运行，已配置健康检查的服务通过检查，Compose 声明的一次性依赖任务按预期完成。无健康检查不承诺业务可用；异常退出、持续重启或超时不得显示成功。部署过程中的镜像准备进度若无法细分，可显示“Compose 执行中”，不能伪造阶段结束。

Docker Compose 的后台返回与健康等待是不同语义，平台需额外核验，且更新可能重建容器。首期明确允许短暂停机，不承诺零停机。[Docker Compose up 文档](https://docs.docker.com/reference/cli/docker/compose/up/)

### 7.2 操作定义

| 用户操作 | 行为与边界 |
| --- | --- |
| 启动 | 使用当前已部署版本和现有镜像启动；不拉 Git、不重新构建。资源不存在时提示重新部署 |
| 停止 | 停止项目服务；保留配置、容器和持久数据 |
| 重启 | 重启当前服务；不更新代码、不应用尚未部署的环境版本 |
| 更新部署 | 检查目标 ref，部署确认后的新提交与配置版本；按 build.command 执行 |
| 重新部署 | 使用选定提交及配置快照；仍按记录的命令策略执行，不暗中改变构建参数 |
| 取消部署 | 请求终止执行并核对现场；已应用的变更可能存在，不能宣称恢复到操作前 |
| 删除项目 | 清理项目容器和自有网络，默认保留持久卷；额外删除数据需要明确选择和二次确认 |

重新部署同一提交不保证获得完全相同的镜像：可变 tag、基础镜像和外部依赖会变化。部署记录应保存实际产物信息，后续基于保留产物实现版本恢复。

新部署在准备镜像阶段失败时不主动停止旧服务。Compose 应用阶段失败可能留下部分新服务，必须标记“部署失败，运行状态待核验/部分异常”；禁止声称自动完整回滚。数据库迁移或脚本产生的数据变更也不属于代码回滚。

服务被新版本移除时，列出将停用的旧服务，确认后仅清理该项目的遗留容器，保留对应数据卷；不盲目全局清理 orphan。

删除先生成任务，保留数据库记录及执行快照，核验归属资源清理完毕后再完成归档。节点失联时显示“等待节点清理”，不得伪报已删。保留卷形成管理员可查的资源记录，避免隐藏占用；不清理 external 资源，不运行全局 docker prune。

## 8. 执行环境与风险约束

独立路由、API 和数据表实现业务隔离；它们不能隔离 Docker daemon、宿主机文件或网络。**建议专用 Git 执行节点作为首期上线条件**，不直接共用现有普通实例的生产节点。共享节点必须另行完成执行面隔离方案评审。

| 风险 | 首期要求 |
| --- | --- |
| Dockerfile/镜像执行任意逻辑 | 仅授权内部用户；构建与运行限额；节点不放控制面秘密；构建环境不挂载生产数据 |
| 特权与宿主机控制 | 默认拒绝 privileged、Docker socket、host PID/IPC/network、设备映射、危险 capability 和越界宿主机挂载 |
| 网络与仓库地址滥用 | 管理员维护 Git 来源和允许的网络目标；拉取请求检查 DNS/重定向目的地；构建及运行网络另行管控，不能只过滤仓库 URL |
| 资源耗尽 | 项目数、服务数、CPU、内存、构建并发、超时和存储额度都有可执行限额；达限阻断并说明原因 |
| 多项目冲突 | 独立 namespace、网络、命名卷归属；拒绝绕过 namespace 的显式共享名称；端口冲突预检并在实际绑定失败时反馈 |
| 持久数据损坏 | 代码和数据分离，更新保留卷；卷定义破坏性变化阻断并要求人工处理，不自动应答删除数据 |
| 密钥泄漏 | 凭证仅按用途授予、输出脱敏、不回显完整 .env；不承诺能识别仓库代码刻意编码后的全部泄漏 |
| 控制面重启/节点失联 | 任务恢复后核对真实容器状态；保留未知状态与待处理任务，不直接标记成功或自动重复执行 |

Compose 原生生命周期 hooks 也属于代码执行，不能因为禁止 shell 拼接就忽略它们。首期策略应明确阻断，待额外操作方案完善再开放。

host.docker.internal 属于独立能力：创建 Git 项目不自动注入 extra_hosts。确需使用时，同时校验用户宿主机访问授权和节点策略；未授权的仓库声明应阻断，不能偷偷删除后继续部署。普通用户页面不增加宿主机访问提示。

白名单降低使用范围，不把可执行仓库变成可信代码。本期提供受控内部工具，不声称已经具备公开多租户安全隔离。

## 9. 管理后台需求

/super/git 必须实际具备以下功能：

- 白名单：检索用户、授权、备注、撤销、历史查询；区别显示 Git 授权与宿主机访问授权。
- 项目：按用户/节点/运行状态查询；查看服务、最近部署与当前运行版本；紧急停止。
- 任务：查看排队、执行、失败、超时、取消及待核验任务；取消指定任务，禁止一键重复所有失败任务。
- 节点：设置 Git 执行能力、允许仓库来源、资源额度、并发、超时；可暂停接收新部署，保留现有运行项目。
- 资源与审计：查看保留卷和清理失败项；记录操作者、项目、提交、动作、结果与时间，不记录秘密值。

节点停用、白名单撤销和项目删除均为独立动作。列表批量操作须明确作用范围，不连带操作旧模式实例。

## 10. 与现有系统的实现边界

现有源码的主要契约是固定 image/version、实例资源、单容器运行信息；生成的 Compose 有固定 alemonx 服务及默认健康和挂载。Git 多服务项目应新增独立业务模型，不能只给 instances 加一个 repository_url 后沿用所有现有流程。

当前入口参考：src/platform_upgrade.go 的 purchaseWithWallet、src/selfhosted_nodes.go 的 createSelfHostedInstance、src/control_plane.go 的 instanceRuntimePayload、agent-core/core.go 的 Compose 生成逻辑、control/v2.go 的 runManagedCompose。这些是设计依据，具体行号在实施时重新核对。

| 层级 | 新模式要求 |
| --- | --- |
| 前端 | 独立 Git 路由、数据状态与请求封装；不出现在现有购买/创建固定镜像流程 |
| API | /api/git/* 与 /api/admin/git/*；独立请求/返回契约；所有入口鉴权 |
| 数据 | 独立项目、服务、部署、授权和资源记录；不走订单、套餐和实例到期逻辑 |
| 任务 | 独立类型、队列和锁；复用通用可靠性基础设施，不套用旧实例业务状态 |
| 执行 | 明确 Git Compose 能力，独立文件目录、资源标签、发现和清理规则 |
| 可复用基础设施 | 身份认证、通用审计、凭证存储、节点连接及通用日志传输 |

建议 API 资源：

| 路径 | 用途 |
| --- | --- |
| POST /api/git/preflights | 检查仓库版本和项目配置，返回提交及预检摘要 |
| GET/POST /api/git/projects | 自己的项目列表；由预检结果创建 |
| GET/PATCH /api/git/projects/:id | 项目详情；保存待部署设置 |
| GET/POST /api/git/projects/:id/deployments | 历史记录；创建部署任务 |
| POST /api/git/projects/:id/start、stop、restart | 当前版本生命周期操作 |
| GET /api/git/projects/:id/services | 服务状态及按服务日志入口 |
| POST /api/git/deployments/:id/cancel | 取消任务并进入现场核验 |
| DELETE /api/git/projects/:id | 创建删除任务，返回任务 ID |
| /api/admin/git/allowlist、projects、deployments、targets | 全局授权、项目、任务和执行节点管理 |

上述为接口边界建议，正式字段、分页和日志流协议在技术设计中确定。不能通过旧 /instances 接口、旧管理操作或 Agent 消息绕过新授权。旧节点扫描、重建和清理不得识别为自己管理的实例；Git 资源应采用独立管理标签，例如 xcloud.git.managed，最终名称由实现统一定义。

## 11. 分期

| 阶段 | 交付内容 |
| --- | --- |
| P0 内部可用 | 独立授权及后台、独立页面/API/模型、Git 连接/同步/版本管理、多 Compose 单元、仓库预检、固定提交、环境快照、命令契约、多服务状态/日志、TCP/UDP 端口管理、持续运行核对、部署与生命周期、持久卷保护、受控执行节点、失败恢复与审计 |
| P1 内部增强 | 额外操作契约、受限脚本执行、更多仓库布局、容器终端单独授权、保留镜像产物后的版本恢复、数据备份/恢复独立方案 |
| 暂不排期 | 公开开放、自动部署、预览环境、跨节点迁移、高可用发布、复杂收费体系 |

## 12. 首期验收标准

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| A01 | 非白名单进入 Git 路由/API | 无入口；直接访问被拒绝；不能通过旧接口绕过 |
| A02 | 管理员加白与撤销 | 无需先创建项目即可操作；记录审计；排队部署在执行前重新检查 |
| A03 | 配置 up -d | 实际命令不追加 --build 或 build-arg；按原生 Compose 策略执行 |
| A04 | 无可选配置 / 配置错误 | 前者用明确默认命令；后者在执行前失败，不偷偷回退 |
| A05 | 命令包含 shell 拼接或平台参数覆盖 | 预检阻断；无宿主机命令被执行 |
| A06 | .env 覆盖、必需值缺失及 env_file | 有效值来源明确；预检与执行一致；缺失阻断；敏感值不回显 |
| A07 | 仓库包含相对路径配置、Dockerfile | 完整版本可用；文件不会变为空目录；更新不破坏旧版本仍使用的文件 |
| A08 | 检查后分支更新 | 创建部署仍绑定已检查 SHA，不执行未检查提交 |
| A09 | 同名服务存在于两个项目 | 服务 DNS 在项目内有效；容器、网络、卷相互独立；端口冲突有明确信息 |
| A10 | web + db + 成功退出的一次性初始化服务 | 正确呈现各服务和项目状态；成功初始化不被误报为常驻服务宕机 |
| A11 | 构建失败 / 应用过程中失败 | 不主动停掉构建失败前的旧服务；部分更新如实标记，不声称已自动回滚 |
| A12 | 点击重启，仓库已有新提交 | 只重启当前版本，不拉代码、不构建、不应用待部署环境 |
| A13 | 连续部署、停止、取消 | 持久卷数据保留；取消后核验运行结果；不全局清理 |
| A14 | 删除、节点失联、清理失败 | 记录保留直到清理核验；可查看待处理资源；不把仍运行的项目显示为已删除 |
| A15 | 超时、控制面重启及重复提交 | 无无限等待和永久占锁；重复提交幂等；恢复先核验，不重复执行不可逆步骤 |
| A16 | 越界挂载、危险字段、无授权宿主机访问 | 执行前被阻断，错误定位到字段或资源；普通用户没有相关提示 |
| A17 | 新旧模式同时存在 | 购买、订单、旧实例重建/扫描/清理不受 Git 模式影响；权限与数据无法串用 |
| A18 | 管理界面与服务日志 | 可按用户/节点/状态追踪任务，按服务看日志；窄屏、错误态及明暗主题可用 |

验收需在真实隔离测试节点上完成：静态解析或前端构建通过不能代替 Docker 构建、持久化、更新失败和节点恢复验证。

## 13. 实施前待确认事项

| 事项 | 推荐默认方案 | 决策影响 |
| --- | --- | --- |
| 执行节点范围 | 管理员维护专用 Git 节点，先不共用普通实例生产节点 | 决定资源隔离与宿主机故障影响范围 |
| .env 缺省 | 无必需变量允许为空；有必需变量则阻断 | 决定纯镜像仓库是否需要额外提交空文件 |

| 默认命令与参数范围 | up -d --build；按本文列出的有限参数支持 | 决定兼容性与执行控制，不能后续隐式改义 |
| 网络开放范围 | 管理 TCP/UDP 映射，默认仅节点允许的地址与来源；公网须显式授权；HTTP 代理为独立入口 | 决定端口池、防火墙与既有代理的接入方式 |

## 14. Git 管理需求

Git 是项目持续管理的对象，不只是创建表单中的一个 URL。仓库同步状态、最新远端版本、已检查版本、已部署版本必须分别保存和展示。

### 14.1 首期仓库能力

| 能力 | 行为 |
| --- | --- |
| 连接管理 | 查看仓库地址、认证方式和可达状态；替换凭证后重新验证；仓库连接异常不影响现有容器运行 |
| 版本选择 | 查询分支、标签与提交；查看当前选择、远端最新 SHA 和部署 SHA；支持明确的提交锁定 |
| 手动同步 | 获取远端信息与代码，不自动构建或替换运行服务；显示是否存在待部署更新 |
| 变更预览 | 比较当前部署与候选提交；突出 Compose、.env、xcloud 配置、端口和卷的变化 |
| 文件查看 | 查看受限大小的文本文件与目录；敏感文件受控显示，二进制不按文本渲染，限制仓库总量和单文件大小 |
| 切换仓库/ref | 保存为待部署设置，重新预检；切换不会立即覆盖当前部署版本 |
| 异常处理 | 凭证过期、ref 删除、强推、仓库删除分别反馈；已有运行版本继续保留 |

不执行针对运行目录的 git pull，也不在当前运行目录中强制 checkout。同步得到候选版本，部署得到不可变发布快照，服务引用发布快照或镜像产物。

Git 管理首期建议只读：同步、浏览、选版本、比较和部署。在线编辑、commit、push 属于仓库写入能力，安排 P1 独立授权；若引入，必须有独立工作副本、未提交变更提示、冲突解决、提交作者与审计。禁止以自动 reset --hard 解决用户改动或以自动 force push 解决远端冲突。平台不把容器中产生的文件变化自动提交到 Git。

仓库内容不确定不等于执行契约不确定。P0 不尝试猜测 npm、Go、Python 项目的启动方式：只检查 Dockerfile/Compose 引用、允许的文件与资源策略。未满足 Docker 契约的仓库显示原因，不根据语言自动生成部署方案。未知业务逻辑由用户负责，平台负责执行和资源边界。

建议新增 Git 项目的仓库状态、ref 查询、同步任务、提交比较和文件浏览 API。它们与部署 API 分开：点击“同步仓库”不能引发服务重启。

## 15. 端口管理需求

端口必须成为可查询、有归属、有分配与释放状态的资源。HTTP 域名只是访问入口的一种形式，不能代替 Docker 端口管理。

### 15.1 区分三种网络含义

| 类型 | 含义 | 产品处理 |
| --- | --- | --- |
| 服务内部端口 | 进程在容器内监听，例如 db:5432 | 平台不猜测所有实际监听；保留项目网络内服务互访，不能据此自动公网开放 |
| 宿主机发布端口 | Compose ports 映射，包含地址、宿主机端口、容器端口、TCP/UDP | 纳入端口资源管理和管理员策略；多个服务分别记录 |
| HTTP 访问入口 | 代理域名指向服务和端口 | 单独授权、配置与检查；不要求数据库必须有域名 |

Docker 官方说明发布端口会映射到宿主机地址，未限定地址的发布可能对外可达。因此，内部白名单不能代替端口暴露策略。[Docker 端口发布文档](https://docs.docker.com/engine/network/port-publishing/)

### 15.2 配置来源与分配规则

Compose 是服务端口声明的来源；平台端口页展示解析结果与实际绑定，不再维护一套暗中覆盖 YAML 的端口定义。

- 仓库声明固定宿主机端口：按声明申请。冲突或不在允许范围时阻断，并定位到具体服务；不静默改号。
- 仓库通过 .env 变量声明宿主机端口：平台可分配端口，把值保存为显式项目环境覆盖，重新预检后使用。界面同时显示变量名、来源与有效值。
- 仓库只声明容器端口并请求动态发布：可以使用 Docker 动态分配，部署后读取实际端口；首期不承诺动态分配端口在重建后不变。需要稳定地址时使用平台分配值或 HTTP 入口。
- expose、Dockerfile EXPOSE 不被自动转换为公网 ports。
- 修改端口进入待部署配置，通过重新部署应用；不能把修改页面显示等同于容器已绑定。
- TCP 与 UDP 分别记录；校验绑定地址、IPv4/IPv6、通配地址重叠和协议冲突，不能只按端口整数做唯一约束。
- 首期限制端口范围、映射数量与允许的绑定地址；未明确支持的端口区间批量映射阻断，不隐式展开无限资源。

平台预分配应原子预留，提交前重检；预检不等于已占用系统端口。实际 Docker 绑定仍可能因外部进程竞争失败，此时反馈绑定失败并核对资源状态。平台不得关闭其他项目或宿主机进程“腾出端口”。

### 15.3 生命周期与界面

端口状态至少包含：待分配、已预留、已绑定、保留未绑定、冲突、待核验、已释放。项目停止后建议保留平台分配端口，避免再次启动被其他项目占用；删除完成且核验映射移除后释放。部署取消或失败时，仅释放确认未使用的新预留，不能误释放旧版本正在使用的端口。

端口页每行显示服务、容器端口、协议、宿主机绑定地址与端口、访问范围、来源、实际状态。管理员可按节点查看全部已分配端口、外部占用和异常记录；节点失联时实际状态显示未知。

公网开放必须经过管理员策略：允许的地址、端口段和来源范围。内网也需绑定正确地址并设置网络策略，不能仅把标签写成“内部”。防火墙/代理规则由平台统一落地并核验，用户 Compose 不得自行绕过策略。host.docker.internal 表达容器访问宿主机，与宿主机对外发布端口分别管理。

## 16. 持续运行与执行任务的关系

GitHub Actions 的 workflow 由触发、job 和 step 组织，可作为本产品部署任务结构的参考。本产品另外维护长期运行的 Docker 资源，不直接兼容 .github/workflows 或 Actions 插件生态。[GitHub Actions workflow 文档](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)

| 执行任务 | 持续资源 |
| --- | --- |
| 同步代码、检查、构建、部署、清理，有开始和结束 | 项目、容器、卷、网络和端口，持续存在 |
| 一次任务成功或失败，保存日志与版本 | 运行状态持续变化，独立采集并展示 |
| 取消任务终止此次操作 | 不自动销毁此前运行项目与数据 |
| 临时构建文件可以按归属清理 | 运行目录、镜像产物引用和持久卷必须保留 |

Agent/控制面持续核对所管理项目的真实服务、网络、端口和资源归属。Docker restart policy 由仓库声明并受策略约束；服务异常要如实展示。首期不因健康检查失败自动拉取最新代码、重新构建或无限重启全部服务。节点重启后先发现与核对已有容器，再按明确恢复策略处理；控制面不可达不要求停止现有业务。

“期望状态”记录用户当前已部署版本及启停意图；“实际状态”来自 Docker。二者不一致显示漂移。首期不自动覆盖用户从外部手动改动的未知资源，管理员可执行受控同步/重新部署；核对任务自身不能成为无限部署循环。

产品的持续性由状态采集、资源归属与故障处理实现，不需要一个永久不退出的部署 job。构建任务结束以后，服务依然运行、日志仍可查看、端口继续占用，存储继续计入额度。

### 16.1 补充验收

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| A19 | 同步仓库发现新版本 | 显示待更新，不构建、不重启；实际部署 SHA 保持不变 |
| A20 | 远端强推、删除分支或认证失效 | 显示具体 Git 状态；已有运行服务不被删除 |
| A21 | Compose 有两个 TCP 服务和一个 UDP 映射 | 全部识别、授权、分配并展示实际绑定；HTTP 入口不代替端口列表 |
| A22 | 两个项目同时申请固定端口 | 仅一个成功预留；另一个有冲突反馈，不关闭现有服务 |
| A23 | 停止、重启、删除或部署失败 | 端口保留/释放符合上述规则，旧服务仍使用的端口不被误释放 |

## 17. 一个项目管理多个 Compose 单元

用户补充的确定边界：一个项目可能启动多个 docker compose。因此，项目不是单个 Compose project 的别名，而是 Git 来源、授权与资源预算下的管理集合。

层级为：Git 项目 → Compose 单元 → 服务 → 容器。部署记录分为项目部署和单元部署；端口、卷和网络同时记录项目与单元归属。

### 17.1 单元登记与配置

创建项目时默认登记根目录 docker-compose.yml 为第一个单元。用户可增加单元，填写名称、Compose 文件相对路径、工作目录和环境文件路径，例如 infra/docker-compose.yml、api/docker-compose.yml、worker/docker-compose.yml。不把仓库里搜到的所有 YAML 自动启动，也不把多份独立 Compose 强行通过 -f 合并成一个部署。

首期建议一个项目对应一个 Git 仓库和一个执行节点；不同单元可使用该仓库不同目录，项目整体部署统一锁定同一个提交。多仓库项目、跨节点单元与单元独立选择任意分支暂缓；单元可以独立部署已选定的项目版本，因此运行时可能存在部分单元旧版、部分单元新版。

每个单元具备独立的工作目录、Compose namespace、环境快照、执行日志、服务状态和生命周期操作。所有单元的资源使用汇总计入项目额度，不能通过增加单元绕过限额。

配置优先级建议为：单元显式覆盖值 > 项目显式共享值 > 单元环境文件 > 根目录 .env 默认值。共享值只用于单元的有效配置解析，不代表自动注入所有容器；变量来源与变更影响应可查看。单元缺省环境文件时使用根目录 .env 默认值，明确指定的文件不存在时阻断。

xcloud.config.yaml 继续只承担命令与额外操作配置，不加入端口、健康、网络或单元编排字段。建议根目录命令作为默认值；单元目录中明确登记的同名配置可覆盖该单元命令，未登记则继承项目默认命令。这个覆盖规则是产品建议，仍需评审；不在本次需求中虚构新的 multi-compose YAML 格式。

### 17.2 项目操作与单元操作

| 操作范围 | 行为 |
| --- | --- |
| 项目预检 | 检查所有目标单元，并合并检查端口、网络、挂载和资源冲突 |
| 项目部署 | 一个父任务包含多个单元任务，按登记次序执行；失败立即停止后续执行，保留已发生结果 |
| 单元部署 | 只部署选中的单元及已确认版本，不隐式更新其他单元；仍检查项目整体资源与冲突 |
| 项目启动/停止 | 按明确次序执行；停止默认逆序；逐单元记录结果，失败时显示部分完成 |
| 单元启停/重启 | 仅作用于该单元；若存在已登记的跨单元依赖，明确提示影响，不暗中停止依赖方 |
| 移除单元 | 先清理其容器与自有网络，持久数据默认保留；不直接删登记后遗留运行资源 |

首期采用用户明确登记的顺序，不自动推断跨 Compose 依赖图。Docker Compose 文件中的 depends_on 仅在对应单元内处理；跨单元的健康等待属于独立编排需求，后续明确依赖规则后再支持，不能通过排序宣称依赖已就绪。

同项目的互斥锁覆盖项目部署、单元部署、端口更改、单元移除等冲突操作；不允许整体部署和单元部署同时改同一现场。执行前给出影响单元列表和已有运行版本。

### 17.3 网络、端口与部分失败

namespace 使用稳定项目 ID 与单元 ID 区分，单元显示名称修改不能创建另一套卷。同名服务 web/db 可分别存在于多个单元，日志与端口页必须先区分所属单元。

不同 namespace 不能解决宿主机端口冲突：infra 和 api 如果都声明同一地址的 TCP 8080，项目整体预检必须阻断。平台自动分配值按单元保存，不能让两个单元共享一个项目级 PORT 值后占用冲突。

不同单元默认独立网络。共享网络或卷须显式登记归属、消费者与删除规则，并符合管理员策略；删除某单元不能删除其他单元仍依赖的资源。P0 不开放任意同名 external 网络/卷来绕过隔离；必要共享资源仅由管理员创建并授权引用。

一个项目部署到第二个单元时失败，第一单元可能已更新，其他单元可能仍运行旧版本。这不是事务性部署。页面应显示“部分部署失败”，列出每个单元的实际提交、状态与失败阶段，并允许选择失败单元重试；重试保持本次提交与配置版本，不自动改成远端最新提交。

项目“正常”须基于预期启用单元的服务状态汇总；存在故障显示“部分异常”，节点不可达显示“未知”；任务“部分失败”与项目当前“部分服务正常运行”可以同时成立。禁止用一个 project.current_commit 覆盖所有单元的真实运行版本。

### 17.4 页面、接口与补充验收

项目概览列出全部单元及部署版本、服务数、运行状态、资源和端口。服务、日志、部署记录按单元筛选。用户能创建/编辑待部署单元、单独预检/部署/启停，也能操作整个项目；配置变更先保留草稿，不立即影响运行资源。

建议增加 /api/git/projects/:id/units 及单元详情、预检、部署、服务和生命周期子资源；项目部署返回父任务与单元任务结果。管理员项目页同样可下钻到单元，不通过旧实例接口代理这些操作。

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| A26 | 一个仓库登记 infra、api、worker 三个 Compose | 分别执行三个独立 Compose 单元，保留三个 namespace 与各自服务，未登记文件不会运行 |
| A27 | 多单元同名服务或同一宿主机端口 | 同名服务可隔离共存；端口冲突在项目层发现并阻断 |
| A28 | 第二个单元部署失败 | 父任务显示部分失败，各单元实际版本清楚；未执行单元不被标记成功 |
| A29 | 仅重启或重部署 worker | 其他单元不拉 Git、不重启；项目额度、端口冲突和互斥仍检查 |
| A30 | 单元独立环境与继承命令 | 展示每个单元的有效配置及来源；环境值不串用，命令不被统一强改 |
| A31 | 删除单元引用共享网络/卷 | 只清理自身资源；仍被其他单元使用的共享资源保留并可追踪 |
